# ToyStoryAI

Telegram/MAX-бот, который превращает фотографию игрушки в персональную
книжку-сказку с картинками. Пользователь присылает фото, выбирает возраст
ребёнка и мораль сказки, а бот в фоне генерирует страницы через DeepSeek и
RouterAI и отдаёт их по одной с картинкой.

## Возможности

- Онбординг по `/start` с кнопкой «Загрузить фото игрушки».
- Приём фото игрушки с валидацией: JPG/PNG/WebP, ≤ 10 МБ, ≥ 300×300 px,
  соотношение сторон 1:2.5–2.5:1. WebP принимается потому, что MAX отдаёт
  загруженные фото уже транскодированными в WebP.
- Диалог из двух вопросов: возраст (3–6 лет кнопками) и мораль из
  курированного списка — свободного ввода нет.
- Распознавание игрушки по фото (`ToyVisionService`): описание внешности
  становится единым источником правды для планировщика, экстрактора,
  судьи и промпта character sheet.
- Генерация в фоне: обработчик отвечает сразу, прогресс сообщается на
  границах этапов («Готовлю сказку…», «Рисую страницы…»).
- Постраничная выдача: сообщение «Страница N» с текстом страницы и одной
  картинкой из уникального каталога прогона `output/{user_id}-{время}/`.
- Частичный результат (пропущены иллюстрации) отдаётся с объяснением и
  одним предложением сделать сказку заново; квота при этом не начисляется.
- Защита от повторного платного прогона: пока идёт генерация, повторное
  нажатие или повторная доставка события отвечают один раз и нового
  прогона не запускают.
- Mock-провайдер изображений, включаемый автоматически без
  `ROUTERAI_API_KEY`, чтобы запускать и тестировать бота без расходов
  (картинки 32×32, при старте пишется предупреждение в лог).

## Требования

- Python 3.11+ (разработка велась на 3.12+).
- Docker и Docker Compose — для контейнерного запуска.
- Токен бота MAX, ключ DeepSeek (текст сказки и распознавание игрушки),
  ключ RouterAI (иллюстрации страниц).

## Получение токена MAX

1. Откройте мессенджер MAX и напишите боту `@MasterBot`.
2. Создайте нового бота и скопируйте выданный токен.
3. Положите токен в `MAX_BOT_TOKEN` в `.env`.

Токен передаётся MAX Bot API **только в заголовке** `Authorization`
(см. раздел «Ограничения MAX API»).

## Настройка DeepSeek

1. Зарегистрируйтесь на <https://platform.deepseek.com> и создайте API-ключ.
2. Укажите его в `DEEPSEEK_API_KEY`.
3. Модель выбирается через `DEEPSEEK_MODEL`: по умолчанию быстрая
   `deepseek-flash`, при необходимости — `deepseek-v4-pro`.

## Настройка RouterAI (иллюстрации страниц)

1. Получите API-ключ RouterAI и укажите его в `ROUTERAI_API_KEY`.
2. При необходимости поменяйте `ROUTERAI_BASE_URL` и
   `ROUTERAI_IMAGE_MODEL` — код не зависит от конкретного вендора.
3. **Если `ROUTERAI_API_KEY` пуст, используется mock-провайдер
   изображений** с картинками 32×32: платные вызовы не выполняются, а при
   старте бота в лог пишется предупреждение. Такой результат нельзя
   показывать пользователям.
4. Соотношение сторон страниц задаётся `STORY_IMAGE_ASPECT_RATIO`
   (по умолчанию `4:3`) и проверяется при загрузке настроек: опечатка в
   `.env` обнаруживается до первого платного вызова. Character sheet всегда
   рисуется как `1:1`.
5. Остальные параметры прогона задаются переменными `STORY_*`: число
   страниц по умолчанию и его диапазон, лимит ревизий, диапазон возраста и
   каталог результатов.

## Пайплайн «сказка-книжка»

По теме, возрасту и морали пайплайн (`app/story_pipeline/`) генерирует
многостраничную сказку с иллюстрациями — `page_1.* … page_N.*` и общий
reference-лист персонажей `character_sheet.*`. Расширение файла соответствует
типу, который вернул генератор (`image/jpeg` → `.jpg`, `image/png` → `.png`):
конвертации нет.

Бот вызывает пайплайн в фоне: `StoryRunner` собирает граф с фото игрушки
как единственным референсом character sheet, уникальным каталогом
`output/{user_id}-{время}/` и асинхронным колбэком прогресса. Тот же
пайплайн доступен как CLI-команда со своими настройками `StorySettings`,
для которой `MAX_BOT_TOKEN` не нужен.

Этапы собраны в явный граф: планировщик → сценарист → экстрактор сущностей →
раскадровщик → судья → (ревизор → судья) не более двух циклов → генерация
изображений. Судья идёт **до** генерации картинок, чтобы не оплачивать
отменённые кадры.

### Запуск

```bash
python -m app.story_pipeline \
  --theme "Приключение плюшевого мишки" \
  --age 5 \
  --moral "Смелость помогает найти друзей" \
  --pages 6 \
  --output output
```

- `--theme`, `--age`, `--moral` обязательны; `--age` проверяется по
  `STORY_AGE_MIN..STORY_AGE_MAX`, `--pages` — по
  `STORY_PAGES_MIN..STORY_PAGES_MAX`.
- `--pages` по умолчанию `STORY_DEFAULT_PAGES` (6); `--output` переопределяет
  корень `STORY_OUTPUT_DIR`.
- Коды выхода: `0` — прогон завершён (в том числе со статусом
  `needs_review`), `1` — постоянная ошибка, `2` — неверные аргументы.

### Режимы изображений

- **Реальный режим** требует `ROUTERAI_API_KEY`: иллюстрации рисует RouterAI
  (`ROUTERAI_IMAGE_MODEL`).
- **Mock-режим** включается автоматически при пустом `ROUTERAI_API_KEY`:
  `MockImageProvider` отдаёт детерминированные PNG без сети и расходов.
  Текст сказки при этом всё равно генерирует живой DeepSeek, поэтому
  `DEEPSEEK_API_KEY` нужен в любом режиме: пустой ключ — понятная ошибка до
  обращения к сети.

### Консистентность персонажа

- Единый реестр сущностей (`ExtractedEntities`) — источник описаний.
- Дословное описание-якорь `Character.full_desc` (внешность + одежда +
  отличительные черты) подставляется в промпт **каждой** страницы.
- Перед страницами генерируется один `character_sheet.*` (recurring-
  персонажи, нейтральный фон, полный рост) и передаётся референсом во все
  страничные вызовы — облик героя не «плывёт» между слайдами. Ровно один
  референс на вызов: фото игрушки (если передано) → лист → страницы.
- Единый `art_style` на всю сказку.
- Гарантия не абсолютна: визуальная узнаваемость проверяется вручную (см.
  «Приёмка пайплайна»).

### Контроль полноты раскадровки

Этап раскадровки проверяет, что на каждую страницу сказки пришлась ровно
одна сцена (`validate_scene_coverage`): пропущенные номера, номера вне
`1..N`, неверное число сцен и дубли `page_num` — это ошибки контракта, а не
мелочи. Нарушения один раз адресно отправляются на перезапрос проблемных
страниц; если после перезапроса покрытие не восстановилось, прогон падает с
`PipelineValidationError` — так же, как сценарист при неверном числе
страниц. Иначе часть страниц осталась бы без иллюстрации при статусе `ok`.

### Стоимость и лимиты

- Текстовые этапы — несколько вызовов DeepSeek за прогон (планировщик,
  сценарист, экстрактор, раскадровщик, судья; плюс ревизор при провале).
- Изображения — `N + 1` генераций за прогон (лист персонажей и по одной на
  страницу). Это основная стоимость; пустой `ROUTERAI_API_KEY` убирает её
  полностью.
- `--pages` ограничен диапазоном `STORY_PAGES_MIN..STORY_PAGES_MAX`, чтобы
  не запустить неограниченный путь расходов.
- Лимит ревизий `STORY_MAX_REVISIONS` (по умолчанию 2): при исчерпании
  прогон не падает, а сохраняется со статусом `needs_review`.

### Результаты

Прогон создаёт каталог `output/{timestamp}/` (метка `YYYYMMDD-HHMMSS`):

```
output/20260927-103000/
  character_sheet.*     # reference-лист персонажей
  page_1.* … page_N.*   # расширение — по типу файла от провайдера
  story.json            # полное состояние прогона (StoryState)
```

`story.json` — полное состояние без бинарных данных: входные параметры,
бриф, тексты и сцены страниц, реестр сущностей, пути и seed изображений,
история вердиктов судьи (`judge_history`), `revision_count`, метрики этапов
и итоговый `status` (`ok` / `needs_review`). Каталог `output/` указан в
`.gitignore` и не коммитится.

#### Seed изображений

Этап иллюстрирования передаёт провайдеру детерминированный seed на каждый
вызов: для листа персонажей — `CHARACTER_SHEET_SEED` (`900`), для страницы
`N` — `page_seed(N) = 1000 + N` (`PAGE_SEED_BASE + N` в
`stages/image_generator.py`). Один и тот же прогон на тех же входных данных
даёт те же seed.

- **Mock-режим** строит PNG именно из seed, поэтому страницы не совпадают
  байт-в-байт, а `seed` в `story.json` заполнен.
- **Реальный режим:** воспроизводимость картинок провайдером не
  гарантируется — поле `seed` может остаться пустым, если провайдер его не
  поддерживает. Выдумывать seed, которого не было, было бы враньём в
  артефакте прогона. Значения seed полезны при отладке и в mock-режиме.

Прогон не может завершиться со статусом `ok`, если PNG какой-то страницы не
написан: этап сверяет фактические файлы с `1..num_pages` и переводит прогон
в `needs_review` с пометкой в метрике этапа.

### Приёмка пайплайна

- **Доля прохождения без ревизии (критерий №3).** Живая серия прогонов под
  маркером `integration` (по умолчанию деселектится):

  ```bash
  pytest -m integration tests/story_pipeline/test_acceptance_metric.py -s
  ```

  Тест прогоняет CLI `DEFAULT_RUNS` раз (по умолчанию 10; число меняется
  константой в файле), считает долю прогонов с `passed=true` без ревизии по
  `judge_history`/`revision_count` и падает, если доля ниже 70%. Нужен
  `DEEPSEEK_API_KEY`; изображения принудительно мокаются, так как метрике
  нужны только вердикты судьи. Без ключа тест пропускается.
- **Визуальная узнаваемость персонажа (критерий №2) — ручной шаг:**
  1. задайте реальные `DEEPSEEK_API_KEY` и `ROUTERAI_API_KEY`;
  2. выполните реальный прогон:
     `python -m app.story_pipeline --theme "..." --age 5 --moral "..." --pages 6`;
  3. откройте `output/{timestamp}/character_sheet.*` и все `page_*.*`;
  4. проверьте, что герой узнаваем на каждом слайде (те же цвет, одежда,
     отличительные черты), фон и стиль единообразны, нет лишних или
     пропавших персонажей;
  5. зафиксируйте вывод в описании изменения: статус из `story.json`,
     номера проблемных слайдов (если есть) и решение «принято/доработка».

## Локальный запуск

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # заполните MAX_BOT_TOKEN и ключи
python -m app.main
```

Бот начнёт длинный polling и будет готов принимать сообщения. При старте
создаётся файл SQLite (`bot.db`) и каталог `uploads/`.

Если токен MAX неверный, приложение завершится с понятным сообщением об
ошибке, без трассировки стека.

## Запуск через Docker

```bash
cp .env.example .env   # заполните значения
docker-compose up --build
```

- Файл `.env` передаётся в контейнер через `env_file`.
- Каталоги `uploads/` и `data/` (там лежит `bot.db`) смонтированы как тома и
  переживают пересоздание контейнера.
- Docker Compose переопределяет `DATABASE_URL` на
  `sqlite+aiosqlite:///./data/bot.db`, чтобы БД жила на томе.

## Проверка подключений (smoke)

Перед запуском бота можно проверить доступы без long polling:

```bash
python scripts/smoke.py                 # MAX + DeepSeek
python scripts/smoke.py --skip-max      # только DeepSeek
python scripts/smoke.py --skip-max --skip-deepseek   # только конфигурация
```

Скрипт проверяет токен MAX через `get_me`, ключ и модель DeepSeek коротким
запросом, а режим иллюстраций лишь сообщает (mock при пустом
`ROUTERAI_API_KEY`). Код выхода `0` — все выполненные проверки прошли, `1` —
была ошибка.

## Тесты

```bash
pip install -r requirements.txt
pytest
```

Тесты не делают живых внешних вызовов: DeepSeek и RouterAI подменяются через
`httpx.MockTransport` или фейковыми объектами, обработчики
проверяются на фейковых событиях MAX. Покрыты валидация фото, распознавание
игрушки, диалог возраста и морали, фоновый запуск и постраничная выдача,
частичный результат, защита от повторного прогона, остановка незавершённых
прогонов и запуск приложения, а также пайплайн «сказка-книжка» на фейковых
провайдерах.

Приёмочные проверки, требующие живых внешних вызовов, помечены маркером
`integration` и по умолчанию деселектятся (`-m "not integration"` в
`pytest.ini`). Они запускаются только осознанно и вручную:

```bash
pytest -m integration --collect-only   # что будет запущено
pytest -m integration                  # живые вызовы, стоят денег
```

## Ограничения MAX API

Эти особенности зафиксированы в коде и должны учитываться при доработках:

- **Базовый URL — `platform-api2.max.ru`** (не `platform-api.max.ru`).
- **Аутентификация только в заголовке** `Authorization: <token>`. Токен
  никогда не передаётся в query-параметрах.
- **Метод `GET /chats` устарел** — для подписок используйте
  `POST /subscriptions`.
- Весь трафик — только HTTPS.
- **Изображения MAX отдаёт транскодированными в WebP** (`i.oneme.ru`), даже
  если пользователь загрузил JPEG/PNG. Поэтому валидатор принимает WebP
  наряду с JPG/PNG; размеры кадра читаются из заголовка WebP.
- В MVP используется длинный polling (`dp.start_polling(bot)`), публичный
  webhook не требуется.

## Ограничения MVP

Вне рамок текущей версии: реальные платежи и подписки (только заглушка),
webhook-режим, горизонтальное масштабирование и очереди, публичный хостинг
изображений, другие языки и типы медиа, админ-аналитика.
