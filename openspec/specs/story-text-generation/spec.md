# story-text-generation Specification

## Purpose
Текстовое ядро пайплайна: планирование брифа, написание страниц, извлечение устойчивого реестра сущностей (персонажи, локации, объекты, единый стиль) и раскадровка, согласованная с реестром. Каждый этап — отдельный вызов языковой модели со своей температурой и строгой JSON-схемой.

## Requirements

### Requirement: Бриф истории (планировщик)
Этап планирования ДОЛЖЕН (SHALL) принимать `theme`, `age`, `moral` и возвращать бриф с полями `logline`, `controlling_idea`, `character_arc` и `narrative_arc` (`exposition`, `rising_action`, `climax`, `resolution`), запрашивая ответ строго по этой схеме.

#### Scenario: Бриф соответствует схеме
- **WHEN** планировщик получает тему, возраст и мораль
- **THEN** результат содержит все поля брифа, включая четыре бита нарративной арки

#### Scenario: Мораль отражается в идее и арке
- **WHEN** пользователь задаёт мораль
- **THEN** бриф использует её как тему повествования и как основу изменения героя, без прямой проповеди

### Requirement: Страницы сказки (сценарист)
Этап написания ДОЛЖЕН (SHALL) принимать бриф и число страниц и возвращать нумерованный список страниц, где каждая страница содержит 2–3 предложения, сенсорные детали, лексику, доступную указанному возрасту, и привязку страниц к битам нарративной арки.

#### Scenario: Число и формат страниц соблюдены
- **WHEN** сценарист получает бриф и число страниц
- **THEN** возвращается ровно заданное число страниц с последовательной нумерацией, по 2–3 предложения в каждой

#### Scenario: Страницы следуют нарративной арке
- **WHEN** страницы распределяются по истории
- **THEN** завязка, нарастание, кульминация и развязка располагаются в порядке, заданном битами брифа

#### Scenario: Лексика соответствует возрасту
- **WHEN** указан возраст
- **THEN** формулировки страниц доступны ребёнку этого возраста

#### Scenario: Неверное число страниц исправляется
- **WHEN** модель вернула неверное число страниц или нарушила нумерацию
- **THEN** выполняется один корректирующий перезапрос, а при повторной неудаче поднимается ошибка

### Requirement: Реестр сущностей (экстрактор)
Этап извлечения ДОЛЖЕН (SHALL) принимать все страницы сказки и описание игрушки, полученное по присланному фото, и возвращать реестр: `characters` с полями `name`, `appearance`, `clothing`, `distinguishing_features`; `locations` с `name` и `description`; `key_objects` с `name` и `description`; и единый `art_style` для всей сказки. Описания героя ДОЛЖНЫ (SHALL) опираться на переданное описание игрушки, а не выдумываться моделью: вид, цвет, наряд и отличительные детали берутся из распознанного описания, чтобы текст и иллюстрации описывали одну и ту же игрушку.

#### Scenario: Реестр извлекается из страниц
- **WHEN** экстрактор получает все страницы сказки
- **THEN** результат содержит персонажей, локации, ключевые объекты и единый стиль иллюстраций

#### Scenario: Описания пригодны для повторного использования
- **WHEN** формируются описания персонажей
- **THEN** они конкретны и визуальны и допускают дословный повтор на каждой странице

#### Scenario: Стиль задан один раз
- **WHEN** формируется `art_style`
- **THEN** он единый для всей сказки

#### Scenario: Описание героя не выдумывается
- **WHEN** в прогоне есть описание игрушки по фото
- **THEN** промпт экстрактора содержит это описание и прямой запрет выдумывать внешность героя, а поля `appearance`, `clothing` и `distinguishing_features` опираются на него

#### Scenario: Описание игрушки недоступно
- **WHEN** прогон идёт без фото игрушки, то есть описание не передано
- **THEN** в промпте экстрактора вместо описания стоит явная заглушка с просьбой выбрать облик героя по тексту сказки, а не пустой блок и не строка `None`

### Requirement: Раскадровка (сценарист сцен)
Этап раскадровки ДОЛЖЕН (SHALL) принимать страницы и реестр и возвращать по одной сцене на страницу с полями `page_num`, `scene_description`, `characters_in_scene`, `location` и `objects_in_scene`, ссылаясь на имена из реестра.

#### Scenario: Сцена на каждую страницу
- **WHEN** раскадровщик получает страницы и реестр
- **THEN** результат содержит сцену для каждой страницы с совпадающим номером

#### Scenario: Сцена ссылается на реестр
- **WHEN** описывается сцена
- **THEN** персонажи, локация и объекты указаны именами из реестра сущностей

#### Scenario: Пустой кадр допустим
- **WHEN** на странице нет персонажей
- **THEN** список персонажей сцены пуст

### Requirement: Проверка и починка ссылок на реестр
Система ДОЛЖНА (SHALL) проверять ссылки сцен на реестр после раскадровки и после каждой ревизии, используя точное, регистронезависимое и нечёткое сопоставление, выполнять один корректирующий перезапрос проблемных страниц и, при остатке неоднозначных ссылок, помечать их для дальнейшей ревизии вместо удаления.

#### Scenario: Неизвестное имя обнаружено
- **WHEN** сцена ссылается на имя, отсутствующее в реестре
- **THEN** выполняется корректирующий перезапрос только для проблемных страниц со списком допустимых имён

#### Scenario: Вариант написания нормализуется
- **WHEN** ссылка близка по написанию к известному имени
- **THEN** она нормализуется к имени из реестра

#### Scenario: Неоднозначная ссылка не удаляется молча
- **WHEN** после перезапроса остаётся неоднозначная ссылка
- **THEN** страница помечается проблемной и передаётся в цикл судья/ревизор, а не тихо исключается из сцены

### Requirement: Полнота покрытия страниц в раскадровке
Система ДОЛЖНА (SHALL) проверять, что на каждую страницу сказки приходится ровно одна сцена с совпадающим `page_num`, выполнять один корректирующий перезапрос проблемных страниц при нарушении (пропущенный номер, номер вне диапазона `1..N`, неверное число сцен, дублирующийся `page_num`) и при остатке нарушений поднимать ошибку, а не создавать прогон с частично проиллюстрированными страницами.

#### Scenario: Страница без сцены исправляется перезапросом
- **WHEN** раскадровщик не вернул сцену для существующей страницы
- **THEN** выполняется один корректирующий перезапрос этой страницы по её тексту, а результат содержит сцену для каждой страницы

#### Scenario: Покрытие не восстановилось — прогон падает
- **WHEN** после корректирующего перезапроса на какую-то страницу сцены по-прежнему нет
- **THEN** прогон прерывается типизированной ошибкой валидации, а не завершается со статусом `ok`

#### Scenario: Дублирующийся номер страницы не приводит к перезаписи файла
- **WHEN** раскадровщик вернул две сцены с одинаковым `page_num`
- **THEN** выполняется один корректирующий перезапрос этой страницы, а в итог попадает ровно одна сцена, так что `page_N.png` пишется один раз

#### Scenario: Номер сцены вне диапазона отбрасывается
- **WHEN** раскадровщик вернул сцену с `page_num` вне `1..N`
- **THEN** такая сцена не попадает в результат и не создаёт лишний PNG-файл

### Requirement: Строгая схема ответов языковой модели
Каждый текстовый этап ДОЛЖЕН (SHALL) запрашивать ответ в формате JSON по схеме соответствующей модели, а схема в промпте ДОЛЖНА (SHALL) формироваться из самой модели данных.

#### Scenario: Схема не расходится с моделью
- **WHEN** формируется промпт этапа
- **THEN** описание требуемой JSON-схемы берётся из модели данных, а не задаётся вручную

### Requirement: Температуры текстовых этапов
Планировщик ДОЛЖЕН (SHALL) использовать температуру 0.7, сценарист сказки — 0.8, экстрактор сущностей — 0.3, раскадровщик — 0.5, ревизор — 0.7; судья использует 0.0 (см. capability `story-quality-review`).

#### Scenario: Температура этапа соблюдена
- **WHEN** выполняется один из текстовых этапов (планирование, написание сказки, извлечение сущностей, раскадровка, ревизия)
- **THEN** вызов языковой модели использует температуру, заданную для этого этапа

### Requirement: Устойчивый разбор ответов языковой модели
Система ДОЛЖНА (SHALL) запрашивать ответ в режиме JSON, снимать возможные текстовые обёртки (блоки кода), разбирать ответ и проверять его по схеме; при схемной ошибке — выполнить один корректирующий повтор, а при повторной неудаче поднять типизированную ошибку, не игнорируя сбой молча.

#### Scenario: Обёртка блока кода снимается
- **WHEN** ответ модели обёрнут в блок кода JSON
- **THEN** полезная нагрузка извлекается и разбирается корректно

#### Scenario: Битый или несоответствующий схеме ответ исправляется повтором
- **WHEN** модель вернула невалидный JSON или JSON, не соответствующий схеме
- **THEN** выполняется один корректирующий повтор с указанием ошибки

#### Scenario: Повтор не помог
- **WHEN** повторный ответ снова невалиден или не соответствует схеме
- **THEN** поднимается типизированная ошибка разбора схемы
