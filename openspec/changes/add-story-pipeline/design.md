## Context

В репозитории уже есть ToyStoryAI: асинхронный бот MAX с `TextGenerator` (DeepSeek), `VideoProvider` (Kling/mock), `Settings`, логированием и герметичными тестами. Новая возможность — автономный пайплайн «сказка-книжка» с иллюстрациями; бот её не вызывает.

Что уже определяет подход:

- Конвенции проекта: `from __future__ import annotations`, полные type hints, docstrings и комментарии на русском, идентификаторы на английском, логирование через `loguru`, настройки только через `pydantic-settings`, повторы через `tenacity`, тесты герметичны (внешние API подменяются, живых вызовов нет).
- Текстовый LLM уже интегрирован: OpenAI-совместимый `chat/completions` DeepSeek с `Authorization: Bearer <key>`, поддержкой `response_format={"type": "json_object"}` и полем `usage` в ответе.
- Задача распадается на изолированные этапы с разными температурами и разными входными/выходными контрактами; между ними есть один цикл (судья → ревизор).
- Единственный новый вендор — генерация изображений (Google Gemini image, «Nano Banana»), вызываемый по HTTPS; он должен быть заменяем и мокаем.

## Goals / Non-Goals

**Goals:**
- Запуск из командной строки `theme/age/moral` → `output/{timestamp}/` с `page_1.png … page_N.png` и `story.json`.
- Визуальная узнаваемость героя на всех слайдах за счёт общего описания-якоря и единого reference-изображения.
- Соответствие сюжета канонам детского повествования, проверяемое LLM-судьёй.
- Явный, наблюдаемый граф состояния: единый `StoryState`, логирование каждого этапа с временем и токенами.
- Заменяемость провайдеров за протоколами; mock-изображения без ключа, нулевой расход при разработке.
- Герметичные тесты, чистые функции для сборки промптов и разбора JSON от LLM.

**Non-Goals:**
- UI (веб, мобильный), платежи, аутентификация.
- Интеграция пайплайна в диалог MAX-бота; существующий бот не затрагивается.
- Оптимизация под продакшн-нагрузку: параллелизм, очереди, кэширование, многопроцессность.
- Генерация видео, озвучка, вёрстка PDF/EPUB.
- Использование LLM для сборки промптов изображений.

## Decisions

### D1: Новая capability — отдельный подпакет `app/story_pipeline/`
Пайплайн живёт в `app/story_pipeline/` со своими `stages/`, `providers/`, `models.py`, `prompts.py`, `pipeline.py`, `cli.py`, `settings.py`. Существующие `app/services/*` не изменяются.

*Почему:* логическая единица (пайплайн страниц + картинок) изолирована от бот-специфичного кода, но переиспользует конвенции и инфраструктуру проекта; тесты и `pytest` не конфликтуют с существующими.
*Рассматривалась альтернатива:* положить этапы в существующий `app/services/` — отклонено, потому что смешивает два продукта в одной папке и делает границы неявными.

### D2: Собственный `StorySettings`, не общий `Settings`
Отдельный `BaseSettings` с переиспользованием имён `DEEPSEEK_*` и новыми `GEMINI_*`/`STORY_*`. Поле `max_bot_token` в него не входит.

*Почему:* `Settings` требует `MAX_BOT_TOKEN` (обязательное поле). Импорт его в CLI заставил бы требовать бот-токен для задачи, которой он не нужен. Отдельный класс не меняет поведение бота и не требует делать токен необязательным.
*Цена:* пять полей `deepseek_*` дублируются — принято как плата за независимый CLI.

### D3: Явный граф состояний на asyncio, без граф-движка
Один класс `StoryPipeline` с протоколом узлов `async def run(state: StoryState) -> StoryState`. Цикл ревизии — явный `while attempt < MAX_REVISIONS`. Отдельного узла-диспетчера нет.

*Почему:* граф линейный (8 узлов) с одним обратным ребром. Явный Python-граф читается лучше диаграммы, требует нуля новых зависимостей (согласуется с правилом «не добавляем зависимости без спеки»), даёт полный контроль над логированием и тривиально мокается. Узлы изолированы протоколом, поэтому будущая миграция на LangGraph локализуется в одном классе.
*Рассматривалась альтернатива:* LangGraph `StateGraph` — отклонена: тянет `langchain-core` и свои абстракции состояния, выгода (checkpointing, conditional edges, human-in-the-loop) для линейной задачи с одним циклом не окупается.
*Рассматривалась альтернатива:* линейная функция без явных узлов — отклонена: цикл ревизии смешался бы с бизнес-логикой этапов, а требование «явный граф состояний» не выполняется.

### D4: Единый мутируемый `StoryState`, сериализуемый без бинарей
`StoryState` — мутируемая pydantic-модель; узлы меняют её in-place и возвращают тот же инстанс, накапливая `StageMetrics` и `judge_history`. Бинарных данных в состоянии нет: изображения хранятся как пути (`PageArt{page_num, path, seed}`).

*Почему:* для линейного пайплайна мутация проще и исключает ошибки копирования; отсутствие байтов делает `story.json` полным и читаемым представлением прогона (критерий приёмки №1) без base64-раздувания.

### D5: `LLMClient` за протоколом, JSON-режим, схема из моделей
`DeepSeekLLMClient.complete_json[T](*, system, user, schema: type[T], temperature) -> (T, Usage)`. Схема JSON не пишется руками в промпте — `render_schema(Model)` рендерит `model_json_schema()` в текст. Транзиентные сбои (сеть/429/5xx) повторяются через `tenacity` до 3 попыток; схемная ошибка (валидный JSON, не бьётся со схемой) вызывает один корректирующий повтор с текстом ошибки, затем `SchemaValidationError`.

*Почему:* промпт и модель не могут разойтись; устойчивость к обёрткам ```` ```json ```` и к неполным ответам изолирована в одном месте и тестируется без сети.
*Рассматривалась альтернатива:* отдельный клиент на каждый этап — отклонено как дублирование логики разбора и ретраев.

### D6: Все промпты — в `prompts.py`
Константы по этапам (`PLANNER_*`, `SCREENWRITER_*`, `EXTRACTOR_*`, `SCENE_*`, `SCENE_REPAIR_*`, `JUDGE_*`, `REVISER_*`) плюс `ART_STYLE_DEFAULT`. Никаких промптов в других модулях.

*Почему:* прямое требование критерия приёмки №5; правки формулировок локализованы и не требуют чтения кода этапов.

### D7: Чистые функции для сборки промптов и валидации
`build_art_prompt(scene, entities)`, `build_character_sheet_prompt(entities)`, `validate_page_count`, `validate_scene_refs`, `validate_judge_verdict` — без LLM и без I/O.

*Почему:* выполнимо требование критерия приёмки №4 (юнит-тесты на `prompt_builder`), а дешёвые детерминированные проверки заменяют надежду на качество промпта.

### D8: Реестр сущностей — якорь согласованности; неизвестные ссылки лечим, а не выкидываем
`ExtractedEntities.characters[*]` даёт дословный `character_full_desc`, повторяемый в каждом промпте. Если сцена ссылается на имя вне реестра: (1) `validate_scene_refs` находит нарушение; (2) один корректирующий перезапрос только для проблемных страниц со списком допустимых имён; (3) при остатке — fuzzy-нормализация к ближайшему известному имени, иначе передача страницы в петлю судья/ревизор, и в пределе `status="needs_review"`.

*Почему:* молчаливый drop ломает соответствие текста и сцены (герой из текста исчезает из кадра) и деградирует незаметно; fail-fast роняет весь прогон из-за правдоподобного дефекта LLM. Трёхступенчатая схема не роняет пайплайн и оставляет исход видимым в `judge_history`/`status`.

### D9: Судья и ревизор — до генерации изображений
Порядок: `Plan → Script → Extract → Scene → [validate/repair] → Judge → (Reviser → Judge)* → Prompt Builder → CharacterSheet → PageImages`. Судья видит только текст и сцены.

*Почему:* правка сцены обесценивает платную генерацию изображения. Судя текст и сцены заранее, мы никогда не рисуем отменённые кадры. Это осознанное отклонение от буквальной нумерации этапов ТЗ ради экономии.
*Рассматривалась альтернатива:* строго по нумерации (картинки, потом судья, потом перерисовка проблемных) — отклонена: `N` платных вызовов выбрасываются на каждой ревизии.

### D10: Единый character sheet как reference для всех страниц
Перед страницами генерируется одна картинка `character_sheet.png` (recurring-персонажи, нейтральный фон, полный рост, `art_style`). Затем каждая страница генерируется с reference = bytes character sheet.

*Почему:* страница 1 как референс тиражирует её ошибки на все последующие; отдельный портрет-якорь развязывает консистентность и от удачности конкретной страницы, и от её сюжета. Цена — одна дополнительная генерация.
*Рассматривалась альтернатива:* reference = первая страница (буквально по ТЗ) — отклонена из-за распространения ошибок; гибрид «sheet + предыдущая страница» — отклонён как избыточная сложность для MVP.

### D11: `ImageProvider` за протоколом; Gemini + Mock
`ImageProvider.generate(prompt, *, seed, reference_images) -> GeneratedImage{data, seed}`. `GeminiImageProvider` вызывает `generateContent` с `inline_data`-частями для референса; `MockImageProvider` (детерминированный PNG из seed) включается при пустом `GEMINI_API_KEY`. Ретраи до 3 попыток — внутри провайдера.

*Почему:* конвенция полностью повторяет `VideoProvider`/`MockVideoProvider`, что снижает когнитивную стоимость и делает тесты и локальный запуск бесключевыми.

### D12: Петля судья/ревизор с жёстким лимитом
Судья (`temperature=0`) возвращает `JudgeVerdict{passed, issues, problem_pages}`. Ревизор (`temperature=0.7`) правит только проблемные страницы (текст и/или сцену). Максимум 2 цикла, затем `status="needs_review"`. Все вердикты — в `judge_history`.

*Почему:* ограниченный бюджет правок предотвращает бесконечный цикл; `problem_pages` делает правку адресной; история вердиктов объясняет итоговый статус.

### D13: CLI и раскладка вывода
`python -m app.story_pipeline --theme ... --age ... --moral ... [--pages 6]`. Создаёт `output/{timestamp}/` с `page_1.png … page_N.png` и `story.json` (`StoryState.model_dump(mode="json")`).

*Почему:* прямое требование критерия приёмки №1; относительный `output/` добавляется в `.gitignore`.

### D14: Тестирование через подставляемые фейки
Чистые функции (`prompt_builder`, валидаторы, разбор JSON) тестируются напрямую; этапы и пайплайн — с фейковыми `LLMClient`/`ImageProvider` и `httpx.MockTransport`. Живых вызовов нет.

*Почему:* риск — пути ошибок (ретраи, схемные сбои, лимит ревизий), а они невоспроизводимы на живых API.

## Risks / Trade-offs

- **Gemini image может не поддерживать параметр `seed`** → Seed фиксируем как `None`, если провайдер его не вернул; воспроизводимость тогда обеспечивается только текстовым промптом. Схема с seed сохранена ради mock и будущих провайдеров. Точная поддержка параметров проверяется при первом живом вызове.
- **Дрейф контракта Gemini image (форма ответа `generateContent`)** → Вендор изолирован за `ImageProvider`; разбор защитный, ошибка логируется вместе с сырым ответом.
- **Согласованность персонажа не абсолютна** → Единый `art_style` + дословный `character_full_desc` + reference-изображение дают лучший достижимый результат; приёмка визуальной узнаваемости ручная.
- **Ненадёжный JSON от LLM** → `response_format=json_object`, схема из модели, снятие обёрток, один корректирующий повтор, затем типизированная ошибка.
- **Стоимость изображений при прогонах** → Пустой `GEMINI_API_KEY` включает mock; судья/ревизор идут до генерации изображений, поэтому отменённые сцены не оплачиваются.
- **Расхождение возрастных рамок** (в ТЗ пайплайна 3–6 лет, в существующем боте 3–10) → Для пайплайна диапазон задаётся настройками `STORY_AGE_MIN/MAX` со значениями по умолчанию 3–6; диапазон бота не меняется.
- **Русский текст дороже в токенах** → Ограничения на 2–3 предложения и N страниц держат объём предсказуемым; лимит токенов берётся из существующих настроек DeepSeek.

## Migration Plan

Дополнение к существующему репозиторию, миграции данных нет. Развёртывание: `pip install -r requirements.txt` (новых зависимостей нет), заполнить `DEEPSEEK_API_KEY` и (опционально) `GEMINI_API_KEY` в `.env`, затем запустить CLI. Откат — удалить `app/story_pipeline/`, `tests/story_pipeline/` и каталог `output/`; существующий бот и его данные не затронуты.
