## MODIFIED Requirements

### Requirement: Единый reference-персонаж для всех страниц
Система ДОЛЖНА (SHALL) создать до генерации страниц одно reference-изображение персонажей (character sheet) по реестру сущностей и передавать его как единственный reference при генерации каждой страницы. Если в прогон передано фото игрушки, лист ДОЛЖЕН (SHALL) строиться с этим фото как единственным reference-изображением, а его промпт — содержать описание игрушки и требование следовать фотографии; если фото не передано, лист строится только по описанию.

#### Scenario: Reference создаётся первым
- **WHEN** начинается генерация изображений
- **THEN** сначала создаётся character sheet, а затем страницы

#### Scenario: Страницы используют reference
- **WHEN** генерируется страница
- **THEN** в вызов провайдера передаётся ровно одно reference-изображение — character sheet

#### Scenario: Лист строится по фото игрушки
- **WHEN** генерируется character sheet и в прогон передано фото игрушки
- **THEN** единственным reference-изображением в вызов уходит это фото, а не лист и не пустой набор, а промпт листа содержит описание игрушки и требование следовать фотографии

#### Scenario: Лист без фото игрушки
- **WHEN** генерируется character sheet, а фото игрушки не передано
- **THEN** лист строится по реестру сущностей, а его промпт не требует следовать несуществующей фотографии

### Requirement: Генерация PNG по странице
Система ДОЛЖНА (SHALL) сохранять по одному файлу на страницу с именем вида `page_N.<расширение>`, где расширение определяется типом файла, полученным от провайдера (по умолчанию — `.png`), передавать провайдеру детерминированный seed, выведенный из номера страницы (для character sheet — собственное фиксированное значение), и записывать в состояние seed, если провайдер его вернул. Конвертация изображения ДОЛЖНА (SHALL) не выполняться: байты сохраняются как есть, потому что добавлять зависимости для перекодирования нельзя. Провайдер, не поддерживающий seed, возвращает `null`, и поле остаётся пустым: воспроизводимость не выдумывается.

#### Scenario: Файл на каждую страницу
- **WHEN** генерация изображений завершена успешно
- **THEN** для каждой страницы существует файл с именем `page_N` и расширением по типу файла провайдера, а в состоянии сохранены путь и seed

#### Scenario: Seed сохраняется для воспроизводимости
- **WHEN** провайдер поддерживает seed и вернул его
- **THEN** значение seed сохраняется в состоянии прогона

#### Scenario: Разные страницы получают разные seed
- **WHEN** генерируются страницы 1 и 2
- **THEN** провайдеру передаются разные seed, выведенные из номеров страниц, а в mock-режиме файлы страниц не совпадают байт-в-байт

#### Scenario: Провайдер не поддерживает seed
- **WHEN** провайдер не возвращает seed
- **THEN** в состоянии сохраняется `null` без выдуманного значения

#### Scenario: Пропущенный PNG не даёт статуса `ok`
- **WHEN** для какой-то страницы сказки файл не записан (сбой генерации, потерянная сцена, номер вне диапазона)
- **THEN** прогон получает статус `needs_review`, а номер страницы фиксируется в ошибке метрики этапа

#### Scenario: Тип файла берётся из ответа провайдера
- **WHEN** провайдер вернул изображение типа JPEG, хотя запрос не задавал формат
- **THEN** файл страницы получает расширение по этому типу, а не `.png`, и байты сохраняются без перекодирования

#### Scenario: Файл листа называется по своему типу
- **WHEN** character sheet сохранён
- **THEN** его имя строится по типу файла, который вернул провайдер, а не по жёстко заданному расширению

### Requirement: Устойчивость генерации изображений
Система ДОЛЖНА (SHALL) повторять временно неуспешные вызовы генерации изображения до трёх раз и при постоянной ошибке не прерывать весь прогон: продолжать оставшиеся страницы и помечать результат как `needs_review`.

#### Scenario: Временный сбой повторяется
- **WHEN** вызов генерации изображения падает с временной ошибкой
- **THEN** система повторяет попытку до трёх раз

#### Scenario: Страница не удалась после повторов
- **WHEN** все попытки для страницы не удались
- **THEN** оставшиеся страницы генерируются, а прогон завершается со статусом `needs_review`

#### Scenario: Постоянная ошибка конфигурации
- **WHEN** провайдер отклоняет учётные данные
- **THEN** прогон завершается понятной ошибкой, не расходуя попытки на нетранзиентную ошибку

### Requirement: Заменяемый провайдер изображений
Система ДОЛЖНА (SHALL) обращаться к генерации изображений через протокол `ImageProvider` и выбирать реализацию по наличию ключа: при пустом ключе — mock-провайдер без реальных вызовов, при непустом — сетевой провайдер, адрес, ключ и модель которого читаются из настроек.

#### Scenario: Mock без ключа
- **WHEN** ключ генерации изображений пуст
- **THEN** используется mock-провайдер и реальные HTTP-вызовы не выполняются

#### Scenario: Детерминированный mock
- **WHEN** mock-провайдер вызывается дважды с одинаковым seed
- **THEN** результат детерминирован

#### Scenario: Выбор реализации по наличию ключа
- **WHEN** ключ генерации изображений задан
- **THEN** используется сетевой провайдер, читающий адрес, ключ и модель из настроек, а не mock

#### Scenario: Mock- и сетевая реализации взаимозаменяемы
- **WHEN** один и тот же этап иллюстрирования работает с mock или с сетевым провайдером
- **THEN** код этапа не меняется: различаются только реализация за протоколом и настройки
