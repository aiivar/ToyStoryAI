## Context

Greenfield-проект: в репозитории сейчас есть только каркас OpenSpec, поэтому этот дизайн начинается с нуля и должен собираться end-to-end после заполнения `.env`. Требования — в `specs/`, мотивация — в `proposal.md`; здесь описаны только технические решения.

Фиксированные внешние ограничения, определяющие подход:

- MAX Bot API обслуживается на `platform-api2.max.ru` (не `platform-api.max.ru`), принимает токен только в заголовке `Authorization: <token>` (без токена в query-параметрах), а метод `GET /chats` устарел (используйте `POST /subscriptions`). Весь трафик — HTTPS. Для MVP длинный polling через `dp.start_polling(bot)` избавляет от необходимости иметь публичный webhook.
- DeepSeek предоставляет OpenAI-совместимый Chat Completions API на `https://api.deepseek.com/chat/completions` с `Authorization: Bearer <key>`.
- Видеопровайдер (по умолчанию Kling AI через GMI Cloud) асинхронен: создать запрос, получить `request_id`, затем опрашивать статус до `success`/`failed`. Генерация занимает примерно 1–5 минут. Image-to-video принимает изображение прямо в теле запроса как base64-строку, поэтому публично доступный URL изображения не требуется.

## Goals / Non-Goals

**Goals:**
- Работающий MVP (`python -m app.main` и `docker-compose up`), удовлетворяющий спекам `bot-conversation`, `toy-photo-intake`, `tale-generation`, `toy-animation`, `generation-history` и `usage-limits`.
- Чёткое разделение: обработчики зависят от интерфейсов сервисов, а не от деталей HTTP вендора.
- Обе AI-интеграции заменяемы конфигурацией, видеопровайдер полностью мокается при отсутствии ключа.
- Полностью асинхронный ввод-вывод, типизированный код, повторы с backoff, структурированное логирование.

**Non-Goals:**
- Реальная обработка платежей и подписок (только сообщение-заглушка).
- Режим webhook/`POST /subscriptions`; транспорт MVP — длинный polling.
- Горизонтальное масштабирование, очереди и многопроцессные воркеры.
- Публичный хостинг изображений для видеопровайдера (Kling принимает base64).
- Вывод не на русском языке, не-toy медиа, админ- и аналитические интерфейсы.

## Decisions

### D1: Слоистая структура пакета, обработчики — тонкие адаптеры
`app/bot/handlers.py` только разбирает события, управляет переходами FSM и вызывает сервисы; весь внешний ввод-вывод и бизнес-правила находятся в `app/services/*`; `app/db/repository.py` отвечает за хранение. Обработчики — единственный слой, знающий о MAX (через `maxapi`).

*Почему:* это удерживает изменения вендора и фреймворка вне бизнес-логики и делает FSM тестируемым с подставными сервисами.
*Рассматривалась альтернатива:* единый `handlers.py` с HTTP-вызовами внутри — отклонена, так как смешивает квоту, валидацию и двух провайдеров в одну нетестируемую поверхность.

### D2: `maxapi` для транспорта MAX
Используем `maxapi` (асинхронная библиотека в стиле aiogram) с in-memory FSM-хранилищем для MVP и длинным polling как точкой входа.

*Почему:* бриф требует `maxapi` и длинный polling; in-memory FSM избавляет от лишней инфраструктуры для однопроцессного MVP. Состояние короткоживущее (фото → стиль → действие), поэтому его потеря при перезапуске допустима — долговечные факты (квота) живут в БД (см. D7).
*Рассматривалась альтернатива:* прямой `httpx` к MAX API — отклонено как избыточное, когда `maxapi` уже берёт на себя заголовки аутентификации и polling.

### D3: Протоколы сервисов с реализациями под конкретных провайдеров
Определяем узкие интерфейсы для генерации сказки и видео. `TextGenerator` реализует вызов DeepSeek. Для видео определяем протокол `VideoProvider` с реальным `KlingProvider` (создание + polling в GMI Cloud) и `MockVideoProvider`, выбираемым при старте, когда `KLING_API_KEY` не задан.

*Почему:* удовлетворяет требованиям mock-заглушки и замены провайдера без ветвлений внутри обработчиков и позволяет тестам подставлять фейки.
*Рассматривалась альтернатива:* один класс с `if not api_key: return MOCK` внутри `generate_video` — отклонено, потому что скрывает стык, требуемый спекой, и усложняет последующую замену провайдера (Replicate, fal.ai и т. д.).

### D4: Конфигурируемость через `pydantic-settings`
Все endpoint'ы вендоров, названия моделей, интервал опроса, максимальное ожидание и URL БД берутся из `.env` через типизированный объект `Settings`; ничего о провайдерах не захардкожено. Значения по умолчанию соответствуют брифу (`deepseek-flash`, `kling-v3-image-to-video`, опрос 10 с, максимум 600 с, 720p std, 5 с, звук выключен).

*Почему:* бриф требует менять провайдера и endpoint без правок кода, а типизированные настройки быстро падают при ошибке конфигурации.

### D5: Повторы через `tenacity`, только для транзиентных ошибок
Оборачиваем вызовы DeepSeek и видеопровайдера в 3 попытки с экспоненциальной задержкой; ошибки 4xx (аутентификация, валидация) классифицируем как неповторяемые, чтобы неверные учётные данные падали быстро, а не сжигали бюджет попыток.

*Почему:* соответствует сценарию спеки «ошибка аутентификации не повторяется бесконечно», при этом поглощая сетевые сбои.

### D6: Async SQLAlchemy 2.0 + aiosqlite, одна таблица `Generation`
Одна таблица `generations` хранит `user_id`, `created_at`, `type` (tale|video), `status`, ссылки на артефакты (`tale_text`/`video_url`/`local_path`), `kling_request_id` и поле ошибки. Одна строка на тип артефакта за попытку; строка видео стартует как `in_progress` с её `request_id` и обновляется до успеха/ошибки после polling. Репозиторий предоставляет историю по пользователю, упорядоченную от новых к старым.

*Почему:* одной таблицы достаточно для MVP-истории и квоты, это избегает преждевременной нормализации, а колонка «type» выражает записи по артефактам из спеки.
*Рассматривалась альтернатива:* отдельные таблицы `tales`/`videos` — отклонено как лишние join'ы без выгоды для MVP.

### D7: Квота вычисляется по истории, а не по состоянию диалога
Решение «бесплатная полная генерация израсходована» выводится запросом к завершённым записям пользователя (завершённая сказка + завершённое видео для одного пользователя), а не из состояния FSM. Генерация, которая так и не отдала оба артефакта, не засчитывается.

*Почему:* напрямую удовлетворяет сценариям спеки о выживании квоты при перезапуске и о неудачной генерации.

### D8: Работа с фото — локальный диск + base64 в запросе
Принятые фото пишутся в `uploads/` для повторного использования, истории и отладки. Kling/GMI принимает изображение прямо в теле запроса как base64, поэтому публичный хостинг изображений не нужен: сервис видео читает сохранённый файл, кодирует его в base64 и подставляет в поле изображения запроса.

*Почему:* провайдер поддерживает base64, и это проще и надёжнее, чем поднимать временный публичный хост: нет внешней зависимости, нет риска, что URL протухнет или будет недоступен провайдеру, и нет отдельного шага загрузки. `uploads/` остаётся единственным местом хранения исходника.
*Рассматривалась альтернатива:* публичный HTTPS-URL через временный или S3-совместимый хостинг — отклонено как лишняя инфраструктура и дополнительная точка отказа.

### D9: Обратная связь о прогрессе из polling
Бот отправляет «Генерирую сказку...» перед вызовом DeepSeek и «Создаю видео (может занять 1–3 минуты)...» перед вызовом видео; сервис видео логирует каждый наблюдаемый статус (`queued` → `processing` → `success`), чтобы операторы могли отслеживать долгие генерации.

*Почему:* удовлетворяет спеку об уведомлениях о прогрессе, сохраняя минимум сообщений пользователю (без спама на каждый опрос).

### D10: Тестирование через подставляемые фейки
`pytest` + `pytest-asyncio` тестируют сервисы сказки и видео с замоканными HTTP/провайдерскими ответами, проверяя построение промпта, поведение повторов, переходы polling, mock-заглушку и таймаут. Живых внешних вызовов в тестах нет.

*Почему:* рискованные части — пути ошибок (повтор, таймаут, статус ошибки) — невоспроизводимы на живых API.

## Risks / Trade-offs

- **Большой base64-payload увеличивает тело запроса (фото 10 МБ → ≈13.3 МБ base64)** → Валидация ограничивает вход 10 МБ; сервис читает файл и кодирует потоково, а при необходимости уменьшает/пережимает изображение перед отправкой. Ошибка чтения или кодирования ведёт к понятному пользователю сообщению вместо некорректного запроса.
- **Задержка генерации видео (1–5 мин) может превысить ожидания или максимальное ожидание** → Настраиваемые `KLING_POLL_INTERVAL`/`KLING_MAX_WAIT`; таймаут оформляется как неудачная генерация, не расходующая квоту.
- **In-memory FSM теряет незавершённые диалоги при перезапуске** → Допустимо для MVP; долговечны только квота и история, и они в SQLite. Пользователь просто присылает фото заново.
- **Реальная стоимость видео (≈$0.42 за 5 с)** → Квота в одну бесплатную генерацию и mock по умолчанию при отсутствии ключа ограничивают случайные расходы при разработке.
- **Дрейф контракта провайдера (форма ответа GMI Cloud / Kling)** → Код провайдера изолирован за `VideoProvider`; разбор ответа защитный, ошибки логируются вместе с сырым ответом.
- **Конкурентность SQLite при одновременных пользователях** → Нормально для однопроцессного MVP с длинным polling; асинхронный движок и слой репозитория оставляют задел для перехода на Postgres.
- **Устаревшие/неверные endpoint'ы MAX** → Централизуем базовый URL (`platform-api2.max.ru`), аутентификацию только в заголовке и избегаем `GET /chats`; фиксируем эти ограничения в README.

## Migration Plan

Greenfield: миграции нет. Развёртывание — `pip install -r requirements.txt`, затем `python -m app.main`, либо `docker-compose up`. Откат — остановка контейнера/процесса; единственное состояние — файл SQLite и папка `uploads/`, их можно удалить для сброса MVP.
