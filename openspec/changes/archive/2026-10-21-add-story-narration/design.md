## Context

Сейчас прогон заканчивается этапом иллюстрирования, а бот отдаёт страницы и «Сказка готова». Требования к поведению — в `specs/`, мотивация — в `proposal.md`. Что важно из устройства кода на сегодня:

- граф пайплайна — линейный список `Stage` (`app/story_pipeline/pipeline.py`), каждый этап получает и мутирует один `StoryState`, метрики копятся в `state.metrics`;
- провайдеры инъектируются в `StoryPipeline` и скрыты за протоколами (`LLMClient`, `ImageProvider`), mock-режим включается пустым ключом;
- настройки пайплайна живут в отдельном `StorySettings` без обязательного токена MAX;
- бот передаёт прогон через `RunRequest` и `PipelineFactory`, доставка страниц — в `StoryRunner`, вложения собираются как `InputMediaBuffer`;
- каталог прогона уникален, `story.json` пишется из `StoryState` после прогона.

Ограничения вендора, проверенные живьём: RouterAI `POST /api/v1/audio/speech` с моделью `google/gemini-3.8-flash-tts` отдаёт только PCM (16 бит, 24 кГц, моно); 66 секунд звука стоили 1,62 ₽ и заняли 25 секунд; лимит промпта — 8192 токена.

## Goals / Non-Goals

**Goals:**

- озвучка не удлиняет прогон: синтез идёт одновременно с рисованием;
- вендор TTS скрыт за протоколом, mock работает без ключа;
- сбой озвучки никогда не отменяет уже готовую книжку;
- озвучка доступна и боту, и CLI, потому что живёт в графе, а не в коде бота.

**Non-Goals:**

- выбор и клонирование произвольных голосов, многоголосая озвучка по ролям;
- фоновое/фоновое-потоковое воспроизведение и стриминг аудио в чат;
- кэширование озвучки между прогонами и повторная озвучка по кнопке;
- изменение квоты, тарифов и платёжной логики.

## Decisions

### 1. Отдельный этап `NarrationStage` + составной узел «иллюстрации и озвучка»

`NarrationStage` — обычный `Stage`: читает `state.pages`, пишет `state.narration_path`, `state.narration_error` и метрику `narration`. Параллельности ради в `StoryPipeline.__init__` этапы иллюстрирования и озвучки оборачиваются в составной узел `IllustrationsAndNarration`, который делает `asyncio.gather` двух стадий и сохраняет имена обоих этапов для прогресса.

Почему так, а не иначе:

- *отдельная фоновая задача из `run()`* — пришлось бы вводить второй механизм жизненного цикла рядом с существующим циклом этапов;
- *последовательно после картинок* — плюс ~3 минуты к выдаче при уже готовом тексте;
- *озвучка внутри `ImageGeneratorStage`* — смешивает две ответственности и ломает тесты провайдера изображений.

Общий `StoryState` мутируется конкурентно, поэтому договорённость жёсткая: этап озвучки пишет только свои поля (`narration_path`, `narration_error`) и добавляет свою метрику, этап иллюстраций — только свои (`images`, `character_sheet`). Между чтением и записью этих полей нет `await`, поэтому в однопоточном event loop гонки нет.

### 2. Провайдер синтеза за протоколом, PCM-нормализация внутри провайдера

`NarrationProvider` (`app/story_pipeline/providers/tts.py`):

```
async def synthesize(self, text: str) -> bytes  # WAV, 24 кГц, моно, 16 бит
```

Голос задаётся провайдеру в конструкторе (прогон использует один голос), поэтому сигнатура остаётся минимальной. `GeminiSpeechProvider` ходит в `POST {routerai_base_url}/audio/speech`, просит `response_format=pcm`, оборачивает PCM в WAV-контейнер стандартным `wave` и передаёт `provider.options.google-ai-studio.speech_metadata.style` с русской манерой чтения из настроек. `MockNarrationProvider` генерирует тишину нужной длительности тем же `wave` — ни сети, ни ffmpeg.

Разбиение по страницам, а не один большой запрос: страница заведомо далеко от лимита 8192 токена, сбой одной страницы не убивает всю озвучку, и повторы адресны. Сегменты синтезируются с ограничением параллелизма (по умолчанию 3 одновременных вызова) и склеиваются в порядке номеров.

### 3. Склейка WAV в этапе, mp3 — через `ffmpeg` с честным запасным вариантом

Склейка — конкатенация PCM-данных с паузой 400 мс между страницами: контейнер один, формат одинаковый, стандартная библиотека. MP3 нужен потому, что MAX надёжно принимает `mp3`/`m4a`, а PCM-в-WAV — не аудио-вложение для мессенджера.

Кодирование делает маленький помощник `app/story_pipeline/audio.py` через `ffmpeg`. Если `ffmpeg` не найден, этап не падает: сохраняет `narration.wav`, пишет предупреждение и метрику, а доставка отправляет WAV как `file`-вложение. Это осознанная деградация: локальная разработка без `ffmpeg` не должна ломать прогон, а в Docker `ffmpeg` ставится в образ.

Альтернатива — кодировать mp3 чистой Python-библиотекой: новая зависимость ради одной операции и худшее качество, чем у системного кодека.

### 4. Голос как вход прогона и как настройка

`Voice` — литерал `"female" | "male"` в `StoryState` и `RunRequest`. Конкретные имена голосов — в настройках: `ROUTERAI_NARRATION_VOICE_FEMALE` (по умолчанию `Kore`), `ROUTERAI_NARRATION_VOICE_MALE` (`Charon`), плюс `ROUTERAI_NARRATION_MODEL` (`google/gemini-3.8-flash-tts`), `ROUTERAI_NARRATION_STYLE`, `ROUTERAI_NARRATION_TIMEOUT`, `ROUTERAI_NARRATION_RETRIES`, `ROUTERAI_NARRATION_CONCURRENCY`.

В диалоге выбор обязателен; в CLI по умолчанию женский голос, чтобы запуск без флага оставался прежним по смыслу.

### 5. Ветка деградации вместо исключения

`NarrationStage` ловит всё, что вернул провайдер, и не выбрасывает `StoryPipelineError` наружу: пишет `narration_error`, добавляет метрику `narration` с `error` и оставляет `narration_path = None`. Статус прогона определяют текст и картинки, как и раньше.

Бот смотрит на `narration_path`: есть файл — отправляет аудио, нет — короткое честное сообщение. Квота и запись о прогоне не меняются, потому что книжка доставлена.

### 6. Наблюдаемость: отдельное сообщение о прогрессе

Составной узел сообщает о границе озвучки через тот же `on_stage`, что и остальные этапы; в `StoryRunner` появляется текст «Озвучиваю сказку…» и защита от повтора, как у существующих сообщений.

## Risks / Trade-offs

- **Озвучка медленнее реального времени (~0,4×)** → на 8-минутную сказку уйдёт ~3 минуты, но она идёт параллельно рисованию; если рисование быстрее, доставка ждёт озвучку — это осознанный размен, потому что пользователь просил один файл всей сказки.
- **`ffmpeg` — новая системная зависимость** → нет его в окружении, прогон деградирует до WAV-файла; в Docker ставится явно, README обновляется.
- **Конкурентная мутация общего `StoryState`** → поля этапов не пересекаются, между чтением и записью нет `await`; тест на параллельный прогон через составной узел.
- **Стоимость (~10–12 ₽ на сказку)** → входит в единственную бесплатную сказку, лимит прогонов не меняется; модель, стиль и голоса настраиваются без правки кода, если цена изменится.
- **Качество русского у Gemini** → проверено живыми пробниками на `Kore`/`Charon`; при смене модели достаточно поменять настройку.
- **Длинные страницы и лимит запроса** → синтез идёт по страницам, при превышении лимита страница режется по границам предложений на несколько сегментов.
- **MAX ограничивает аудио 256 МБ и 60 минутами** → сказка на 12 страниц далеко ниже обоих пределов; ограничение фиксируется в README как известное.

## Migration Plan

1. Заполнить `.env`: `ROUTERAI_API_KEY` уже нужен для картинок, новых ключей нет; при желании задать `ROUTERAI_NARRATION_*`.
2. Пересобрать образ — в `Dockerfile` добавляется `ffmpeg`.
3. Обновить README и `.env.example` вместе с кодом.
4. Откат: озвучка не имеет отдельного ключа, поэтому откатывается возвратом предыдущего образа; данные прогонов (включая `narration.mp3` и `story.json`) совместимы в обе стороны, потому что новые поля состояния необязательные.
